# Native runtime contract

S3: One Home owner obtains an OS file lock. The app and internal CLI use the same Mac runtime. A second writer is refused. The internal CLI attaches to the current owner through an authenticated Unix socket with same-user peer checks and an ephemeral Home-held capability. The short socket path is in a user-owned private temporary directory and binds to the canonical Home path. Request and reply frames, client concurrency and time are bounded. No TCP listener is opened; this is not qualification of the optional server or the full CLI grammar. The initial attachment cannot read Incognito. Observer disconnection does not cancel accepted owner work. Native UI submits typed intents; it cannot authorize tool effects by displaying a proposal.

S4/A2: All db.md record mutations use the official bundled dbmd executable with explicit arguments, a bounded response and timeout. Native recovery intents and integrity commitments live separately from disposable UI state. Before a new save, compare the expected canonical revision; on conflict preserve both versions and stop writes. Write and synchronize intent before create-only artifact publication and record mutation; recover only exact intended bytes. Never promise a multi-file atomic transaction or infer power-loss safety from process-crash tests.

Since September 24, saving runs beside the runtime rather than inside it. A change applies to the runtime's state in memory and returns at once. One writer saves the latest state; changes made while a save runs join the next one, so each save writes everything changed so far and nothing is skipped. Every save still verifies the Home first. Callers whose promise is durability wait for their change to reach disk: accepting a message, a draft reported as saved, approving a document, app or skill, marking reviewed file changes as applying, continuing Home messages in a thread, backup, sleep and quit. A run starts only after its acceptance is on disk. A failed save keeps the changed state and its artifacts and files for the next attempt and reports the failure; a conflict holds every write until the person reviews it. An app record is written with the save that takes it or not at all, and the app hears success only once it is on disk.

Engine turns contain text, a complete proposed-call set and a finish status. Validate the entire set and successful terminal status before executing any tool. Truncation, malformed calls, cancellation, runtime failure or undeclared arguments prevent the set from executing. Tool results are inert history; only the native owner starts the next generation. Cancellation is a thread-safe signal outside the blocked inference executor and is rechecked before each effect.

Source tools. The first slice (September 14) offered source.list, source.stat, source.search, source.read, source.extract and artifact.propose over one read-only folder per thread and left rich formats unavailable. Since September 17 the runtime offers the access-grouped tools described under Sources, documents and helper isolation; artifact.propose is unchanged. The model sees runtime-issued file IDs and relative display paths. Files are opened component by component through directory handles with O_NOFOLLOW, non-regular files are rejected and identity is revalidated. Source excerpts carry exact source SHA256, UTF-8 byte range and citation ID. New runs preserve the returned text as immutable source-event documents and in the current run, so native review can inspect it after detachment. The excerpt is evidence of the bounded read, not a complete copy of the external folder. File metadata is checked before and after reading; a changed source is refused. A source cannot issue instructions, admit memory or authorize writes.

The first slice's bounds were 200 files, depth 8, a 1 MiB text-file ceiling, 20 inventory and search results, 8 KiB excerpts, 32 KiB of returned source text, 8 tool rounds, 6 calls per model turn, 64 KiB of artifact content and a 10-minute job deadline. The current bounds are stated in the sections below; artifact content keeps its 64 KiB ceiling. All of them are safety ceilings to test, not measured performance claims. Limits belong beside their implementation and should change only with evidence and updated fixtures.

artifact.propose is inert. Native review shows full content, filename and source citations. The approval binds thread, pending proposal and exact proposal, filename, content and citation digest. Publication is create-only. Duplicate or stale approval cannot overwrite or silently repeat an effect. A started durable commit reconciles to a truthful outcome across interruption.

U1/U4: Persistent input is accepted before clearing its draft. Draft revision comparison rejects an out-of-order autosave, and submission advances that revision so a pending save cannot restore sent text. Autosave waits for a 300 ms pause in typing but saves at least once a second while typing continues, one write at a time. Duplicate nonce plus identical input resolves to the same run; changed input under an old nonce is refused. One active model run serves queued threads serially. A thread awaiting approval cannot accept a new turn. Incognito content bypasses disk, search, memory admission and artifacts, and is discarded on close. Forget suppresses future AI use with source lineage, rather than erasing visible evidence. Correction preserves the old record, excludes its recall, and admits a replacement with a supersedes link. Combined shared/thread-only/Incognito/correction/Forget fixtures exercise the model context, not only UI labels.

Mac records now have a compact Home index, independent thread/draft records, immutable conversation and excerpt events, and a native recovery/hash ledger. Four process-termination seams exercise replay of an interrupted artifact-plus-record commit. A bounded native Home backup and inert restore now pass the scoped checks below. Full interoperability, scale and power-loss qualification remain open.

Model setup calls the existing pinned WeightStore APIs behind an explicit user action. A runtime maintenance gate excludes inference until setup ends. Download cancellation drains library workers; hash verification and engine initialization do not yet prove the strict native Stop/quiescence budget. Fresh download, repair and cancelled acquisition have not been independently exercised by this app receipt.

## Adversarial corrections and current limits
The complete model response is validated before the first tool executes. Artifact proposals must be the sole call. A `tool_calls` finish with no calls is refused. Invalid IDs, content or termination and unrelated undeclared tools remain hard failures. For extra argument keys or a known declared name spelled with `=` instead of `.`, the host can request one corrected response within the existing job round/deadline ceilings. No portion of the rejected set executes, spelling aliases are never executable, and the new response must independently pass validation. Approval authority is unchanged. Scripted correction/exhaustion/no-partial-execution/rejection cases and the final real Cedar replay pass. Correction feedback is appended to the leading system message; the pinned template rejects a late system-role message. No new user turn or executable alias is fabricated. A proposal the host refuses for something the model can fix, an app id that matches nothing, a document without citations, an app that is not one bounded HTML document, returns as a tool result like any other tool error, at most twice in a job, with nothing staged in between; the round and time budgets still bound the job. It used to end the job instead, which left the person with no proposal and no way on.

The words a model writes before a working tool call say what it is about to do. The runtime shows them as one line of the run's Activity, bounded to 280 characters, ahead of the calls they introduce, and leaves them out of the reply. The reply is the final round's text, or the text beside a proposal. If the final round has no text of its own, the reply keeps what the model wrote along the way, so a finished job never ends with an empty reply.

Journal uses the same production draft coordinator as conversation input. Its native runtime adapter persists an accepted entry, remaining draft, revision and idempotence receipt together. Delayed acceptance, lost acknowledgements, concurrent edits and fresh-process restart are tested. Retained prior runs keep historical documents and citation ownership stable after later turns; the compact root index and current-run IPC do not include that historical payload. Invalid publication/state identities are validated before recovery intent. Public mutations refuse a closed owner.

Canonical Home binding accounts for supported macOS system path aliases after creation and in a genuinely fresh URL/process; user-created symlinks still refuse. Model hash verification has cooperative checks between bounded reads and during file status work. Since September 24 the app starts that check at launch, at utility priority, when every model file is present and Low Power Mode is off; the first message joins it and Stop ends the wait. The proof stays with its inference owner, and model setup cancels a check still running. Native model Check and Stop were observed; complete load/stop quiescence and fresh download qualification remain separate open gates.

Eligible memory admission is idempotent. Context selection ranks permitted memories by lexical overlap, thread affinity, recency and stable ID. It includes whole records within 4,096 bytes and at most 12 records. Recent complete exchanges plus any pinned Home exchange fit a 16,000-byte history policy; up to 2,000 bytes may hold explicitly partial, ID-bound excerpts of omitted history. These are bounded development operating policies, not measured semantic-recall or model-capacity claims. Oversized current input or a pinned exchange is refused with original text retained. The independent engine token bound remains authoritative and can refuse source-heavy later rounds. Revise these budgets only with measured task/context coverage and headroom evidence; no public override claims are introduced.

Context receipts preserve selected message and memory IDs, partial earlier excerpts and omitted counts before inference. The native inspector exposes exact included conversation text and distinguishes later tool reads. Forget excludes the exact event and its derived excerpt from future selection. Newly created Thread only records can read shared memories and write thread-local memories. Existing strict records with no explicit read choice remain strict until current user opt-in; promotion preserves that choice. Incognito reads neither saved memory nor persistent drafts.

Home backup profile `sevra-home-v1` captures the declared ordinary owned files and SHA256 manifest, excluding device authority/control, caches and Incognito. The bounds are 20,000 visited entries, 512 MiB total, 64 MiB per file and 8 MiB for the manifest. These are conservative desktop transfer resource limits, not maximum-supported-Home claims. Exceeding one refuses the complete transfer instead of producing a partial success. Qualification on large actual Homes is the revision gate. The exporter binds inventory and hashes to a completed owner view; restore verifies closure, paths, case/Unicode collisions, ordinary-file identity and official dbmd validation before create-only publication. macOS system aliases resolve to physical destination parents. Restore never replaces a folder or publishes inside the source backup. Only the exact old Home template receives its staged missing-owner migration.

Restoration creates fresh native control/integrity state. It copies no source grants, endpoint credentials or queued execution authority. A dated review keeps AI and artifact publication paused until explicit activation. Known newer same-Home Forget records merge monotonically; unknown later privacy epochs remain disclosed. Enabling AI does not resume previous work or approve a saved proposal. The original external source files and model/runtime dependencies remain separate from owned Home completeness.

External valid `sevra-draft` changes are reviewable through exact file digests. Adoption preserves the edited file and acknowledged predecessor text when available in `records/drafts/conflicts`, then advances the draft revision through the ordinary recoverable transaction. After restart, an unavailable predecessor is reported rather than invented. Concurrent changes invalidate the review. A competing unsaved composer retains its two-version choice. Missing, malformed, immutable-source and other runtime-owned changes cannot be adopted as drafts. Draft/conflict records are never conversation sources or automatic memory.

## Thinking before answers
Thinking is a per-thread switch, off by default and absent from Home unless a person turns it on. When on, each answer in that thread may reason first; the switch persists with the thread record and applies to the next answer, never to a running one. A tool turn thinks as well: the person's switch decides, not the attachment, and reading files is where people ask for it most. A thought shortens only a plain answer, to its 1,024-token reply cap; a turn that can stage a change, a document or an app keeps the job's whole reply budget, because the thought has a budget of its own. Older runs that recorded an `offForTools` receipt, from when an attachment dropped the switch, still decode.

The runtime asks the engine for the model's `low` effort with an explicit budget of 768 thought tokens and a 1,024-token reply; the model's own default effort (`xhigh`) is never left implicit. The thought is bounded three ways: the model closes it, the budget ends it, or Answer now ends it. In the last two cases the documented closure sentence and the close tag are appended, so a bounded thought always yields an answer rather than an empty reply. The thought and answer run through one engine-held `generatePhased` session with independent sampling and output budgets. The answer continues the live state, consuming any pending token exactly once and reading only the transition suffix. A later conversation still uses the ordinary cold-equivalent prefill-boundary rule; generated thought state never becomes a fresh-equivalent checkpoint. Response metrics record the actual work of both phases. See [[records/measurements/prompt-speed-qualification-2026-09-21]]. The thought uses the model card's thinking sampling profile with a per-run seed derived from the run id, so it cannot loop the way greedy decoding can. The answer phase keeps the app's greedy sampling within a 1,024-token reply cap, and an answer that outruns that cap fails the run as before while keeping an accurate receipt. Plain turns use the reply budgets under Context and job budgets. Prompts are encoded through the engine's spliced path so an assistant turn the engine produced, thought block included, re-encodes from its held ids. Flipping the switch changes the system instructions the template renders, so the next turn after a flip re-reads the conversation.

Only a receipt is recorded with the run: level, budget, thought tokens, seconds measured from the first thought token, how the thought ended (`closed`, `budget`, `answerNow`, `stopped`, `offForTools`) and, for a job that thought before more than one model round, the number of `steps`. The receipt covers the whole run: each round's tokens and seconds add up, the latest round says how thinking ended, and a round whose response the host refused keeps its thought, since that thought was real and visible. Receipts recorded before `steps` existed read as one step. The thought text is working state: it streams to the observer while the thought runs, stays readable in process memory as one entry per thought, within 64 KiB per run, for at most the eight most recent runs while Sevra is open, and is never written to Home records, conversation sources, backups, search or memory admission. The live observation also says how a finished thought ended, so the line above a reply is exact while the answer is still arriving. Incognito thoughts stay in memory and leave with their thread. Answer now is a thread-safe signal read between thought tokens, outside the blocked inference executor; it ends the thought, never the run, and is a no-op for a thread that is not thinking. The local endpoint exposes `think` (`on`/`off`) and `answer-now` as ordinary typed intents; the internal CLI has `--think` and `answer-now`. These budgets are development operating bounds chosen for a local decode rate of a few to sixteen tokens per second, not measured optima; revise them with paired measurements of answer quality and wall time.

## Response metrics
Each run records `metrics`: the engine's own statistics for its model requests, numbers only. Reply tokens and their decode seconds; thought tokens and their decode seconds; prompt tokens the model computed and their prefill seconds; tokens the first request reused from an earlier state of the conversation, which the engine offers only at its own prefill pass boundaries, so a conversation shorter than the first boundary records none; the largest prompt and the context window; the time from the start of the first request, after any model load, to its first generated token; the model load time when the response had to load the model; model rounds; the decode-phase expert cache hit rate, weighted by the tokens each request wrote; and the total process budget the plan was sized to, the person's limit when they set one, with whether they did. A job sums its rounds, including a round whose response the host refused, since that time was spent. A round that fails before the engine returns records nothing. Runs recorded before `metrics` existed decode without it. The numbers stay with the run in the Home and are never sent anywhere.

While a response runs, the snapshot carries its live writing speed, `GenerationObservation`: the phase (thinking or writing), its tokens so far and the time between its first and latest token, memory only. The rate is the intervals between arrivals, so it changes only when a token arrives and a first token claims no rate. Answer tokens are counted where the engine yields them, because tool-call markup can hold text back. The internal CLI prints the same speed line after a response. `LocalInference.lastStats` keeps the engine's statistics for the last turn so a real check can compare them with what the run recorded; `sevra-mac-checks --real-metrics` does that for a thinking turn that loads the model, a second thinking turn that resumes the conversation from a pass boundary, and a plain turn after switching thinking off, which reads the conversation again.

## Sources, documents and helper isolation
A thread holds up to eight attachments: files, folders, or db.md stores (a folder whose top level holds an ordinary `DB.md`). Each attachment has an access choice, read only by default or can propose changes. The person sets it in native UI; the model never can. A selected file authorizes only itself, never its siblings. Since September 23, a folder grant retains its root descriptor without recursively inventorying the tree. There is no attachment file-count or tree-entry limit. New operations inspect current directories; source.list browses immediate subfolders, source.find locates literal text in relative paths, source.search searches current contents within an optional scope, and source.read accepts a returned path ID or an explicit attachment and relative path. IDs bind to the selected root and path, never an inventory index. Every open walks from the root with O_NOFOLLOW, rejecting links, special files and parent traversal. Hidden paths require an explicitly selected file. Broad recursive operations skip dependency and application bundles, while explicit scopes can inspect those folders. A new scan sees creates, deletes and renames without reattaching. Read caches also bind device/inode, so atomic editor replacements invalidate them.

Work is bounded per operation, not by total folder size: at most 4,096 visited entries and a two-second cooperative deadline between bounded reads; document helpers retain their separate timeouts. Listing or finding returns at most 40 entries, content search at most 20 matching lines, and each result array targets at most 16 KiB. Recursive traversal retains at most 32 directory levels; deeper subtrees are reported and can be reached by an explicit narrower scope. A session retains at most eight opaque cursors for fifteen minutes of inactivity. At most 64 native directory streams are leased across all sessions in the process; inactive cursors are evicted under pressure and explicitly require restart. Darwin directory cookies are not portable across newly opened DIR streams, so a continuation keeps its native stream. It verifies root-relative directory identity and timestamps before and after each page. A changed directory requires restarting, and a changed file or extracted text invalidates a within-file search position. Cursor use binds the original tool, query, match mode and scope and consumes the previous token. Skips and unreadable coverage are explicit. These are operating bounds tested with live mutation, pagination, cancellation and resource pressure, not measured optima. They are internal defaults; relative scopes and new operations are the supported way to narrow work. Revise them when corpus timings, descriptor use or model-round costs justify it. See [[records/decisions/sevra-live-folder-navigation]].

The same file or folder cannot be attached twice. Attaching, detaching and changing access are allowed while a run waits for review and refused while a run is working. Detaching revokes path IDs, cached bytes and cursors. Folder access lives in the running process, so after a restart the person attaches the folder again. Thread only limits remembered context, not explicit source access. The attachment chip describes a live folder without inventing a total file count. Home reconciliation is offered only when storage actually needs review, not for ordinary attachment errors.

Tool groups follow trusted state. Any attachment offers source.list, source.find, source.search, source.read and artifact.propose. A changeable file or folder adds file.create, file.edit and file.write; new files can only be created inside a changeable folder. An attached store adds kb.search and kb.query, and a changeable store adds kb.create, kb.append and kb.edit. File tools never touch a store and record tools never touch other files. An app request, `/app`, or a thread that owns an app adds app.propose and app.read; `/skill` or an explicit skill request adds skill.propose. Incognito removes every change, app and skill group. Each response is validated against the tools offered for that job: an unoffered tool fails the whole response before anything runs, and proposal tools must be the only call. Offering a tool grants no effect.

The system instructions name each attachment on its own line, the name quoted as data and bounded to 120 characters, with its attachment ID, kind and access. Without attachments, the model is told it runs locally and that the person can grant live read access with the paperclip. They say that a request's "this", "it" or "the file" means those attachments, to be read before answering. Told only that files were attached, a model asked "what is this?" about one attached PDF asked what "this" meant instead of reading it.

Text files up to 8 MiB are read as UTF-8; NUL bytes are refused. PDF, RTF, Word (`.doc`, `.docx`), OpenDocument text, Excel (`.xlsx`) and EPUB files up to 64 MiB are extracted into page text joined by a form-feed separator, and citation byte ranges and pages refer to that deterministic text. Images (PNG, JPEG, HEIC, TIFF, GIF, WebP, BMP) and PDF pages without a text layer are recognized when a read covers them: at most 20 pages per helper request and 40 per job. Such citations are marked `ocr` and carry a recognition-error note. Search is literal and ignores case and accents; an explicit words match mode requires every word on a line. It reports pages for multi-page documents, extracts at most 8 new documents and scans at most 256 MiB per call, returns at most 20 matches, reports where to continue, and names documents whose scanned pages it could not see. A read returns at most 8 KiB, and one job returns at most 64 KiB of source text, about 16,000 tokens. Read bytes and extracted text are cached by device, inode, size, modification and change time within 96 MiB and 256 entries. A document that failed extraction fails again from that cache without rerunning the helper. Password-protected, damaged, oversized and unsupported documents are refused with a reason. Layout, tables and columns become plain text. A stopped or failed job discards whatever it staged. A file changed after the model read it must be read again before staging an edit; apply-time verification still binds approval to the exact reviewed base.

Rich formats are parsed only by the bundled `sevra-extract` helper: one short-lived process per request, given the document's bytes on standard input and never a path. Before it reads input, the helper applies a deny-by-default Seatbelt profile through `sandbox_init`. Reads are limited to system libraries and data, fonts, its own executable and a private per-request folder, and writes to that folder. It has no network, cannot launch programs, cannot reach the window server, and can reach no services beyond logging, fonts and directory lookup. The scripted suite runs the helper's self-test under the strict and recognition profiles: reading a user file, listing its folder, writing beside it, connecting to a loopback listener, launching a process, reaching the window server and reading the home folder all fail. Text recognition is split in two. A strict render stage turns the file into validated grayscale frames at most 1,600 pixels on a side. A recognition profile, which may reach the GPU and Neural Engine, receives only those frames and first proves recognition works on a rendered canary. Word, Excel and EPUB use the pinned dbmd extractor inside the strict profile, which may launch only that executable. The runtime bounds each helper's time (60 seconds for a document or render stage, 120 for recognition, 30 for a knowledge operation) and output. It also bounds the physical memory footprint of the helper's whole process group, including a dbmd it starts: 1.5 GiB for documents and 1 GiB for knowledge operations. The scripted suite confirms that this measurement counts a process the group leader starts. The helper sets its own CPU and file-size limits. On any excess or cancellation the runtime stops the helper. It observes exit without reaping, kills the whole process group, waits up to 5 seconds for output to drain, then reaps. A helper killed mid-request can leave its work folder behind; the next helper removes such folders after 15 minutes, before it enters its sandbox.

Known residuals. `file-read-metadata` stays global because PDFKit and Vision need it, so a helper can learn whether a path exists and its size and dates, but not its contents. In the dbmd modes, dbmd canonicalizes its working folder, so those profiles may also list the folders above the private folder and above an attached store. `sandbox_init` is deprecated in favor of App Sandbox entitlements. The app itself is not yet App Sandboxed or signed for release, so this isolation covers the parser processes, not the app.

## Reviewed file changes
Change tools stage and never write. file.create takes a relative path inside a changeable folder: no hidden or parent components, at most 10 components and 512 bytes, and a text type. file.edit replaces text that must occur exactly once; file.write replaces the whole text. Both require the file to have been read in the same job, to be text of at most 1 MiB, and to have an editable type. Sevra never creates or changes shell scripts, HTML, SVG or notebooks. Later edits to a staged file build on its staged text. One job stages at most 24 files and 2 MiB. When the job ends, the run waits for review with the set, a line diff for each change (two lines of context, at most 600 lines, lines clipped at 400 characters) and the complete new text.

Approval binds the exact set: change IDs, operations, paths, base hashes, content digests, record type and summary, and each attachment's device and inode. The runtime refuses a stale digest, a set no longer awaiting review, a missing attachment and a read-only one. Before writing anything it reads every base again. If one differs or a new path now exists, the whole set is refused unchanged. It saves each previous version under `changes/<set>/` in Home and records a manifest, without contents, before the first write and after each one. Each file is written to a temporary sibling and confirmed with F_FULLFSYNC, keeping mode, extended attributes and ACLs, so Finder tags survive. It is then exchanged with RENAME_SWAP. The swapped-out file must match the reviewed base hash and inode; otherwise the exchange is reversed and the person's version kept. New files are placed with RENAME_EXCL. Files with other hard links are refused. The first failure stops the set: that change is marked as a conflict, later ones are skipped, and the set is partial.

The set is marked as applying before the first write. If Sevra dies while writing, the next launch reports which files its manifest recorded as written, replays nothing, and lets the written part be undone once the folder is attached again. Undo walks written changes in reverse and requires each file to still match what Sevra wrote. A changed file gets its saved previous version back through the same verified exchange. A new file is moved by handle into a private sibling folder, verified by inode and hash, and moved to the Trash from there, so a path swapped for a link is never followed. Its Trash location is recorded for Show in Trash, and folders Sevra created are removed when empty. A file edited after Sevra wrote it is left alone and reported. Discarding a set writes nothing and clears its staged text. Incognito threads can read attachments but are never offered change tools.

## Knowledge bases
A folder whose top level holds an ordinary `DB.md` attaches as a knowledge base and is not inventoried. kb.search takes a regular expression and kb.query a record type and one key=value filter. Both run the pinned dbmd through the helper's `store` mode: the strict profile plus read access to that store alone, and write access only when an approved change is written. Only the verbs search, query, show, schema, write, body, stats and index are accepted, and write verbs require the helper's explicit write flag. Results are limited to 40 and register record IDs that source.read opens.

Record tools stage like file tools. kb.create needs a store-relative Markdown path under `records/` or `sources/` that is not an index or log, a simple type and a one-line summary under 200 characters. kb.append and kb.edit change only the body of a record under `records/` that was read in the same job. `DB.md`, `index.md`, `index.jsonl`, `log.md`, frontmatter and existing sources are never changed. Approved records are written by dbmd (`write` and `body set`) with the body passed on standard input, so indexes stay current. dbmd may file a new record by its type; the review then shows the path it chose. dbmd has no compare-and-set, so the runtime checks each record's reviewed base again immediately before dbmd rewrites it. An edit made while earlier changes in the set were being written is kept and reported. A narrow window remains between that check and dbmd's own write; closing it needs a compare-and-set in dbmd, whose `body set` takes no expected hash. Undo restores each record's previous bytes through the verified exchange, moves new records to the Trash and rebuilds the store index.

## Skills and mini-apps
Skills and mini-apps are user-owned, versioned Home content, and the model can only propose them in jobs where their tools are offered. A skill proposal has a name of 2 to 32 lowercase letters, digits and hyphens (`app`, `skill` and other reserved names are refused), a one-sentence description, instructions up to 16 KiB and declared tool groups: read, change, knowledge or apps. Approval binds the proposal digest, publishes `extensions/skills/<id>/<version>/SKILL.md` create-only through the recoverable Home transaction and turns that version on. A request that starts with `/name` follows the active version, whose file is hash-checked before inference; a changed file fails the run before any model call, and an inactive or removed skill is not used. Declared read, change and knowledge groups grant nothing, because attachments and their access decide those. A skill that declares apps offers the app proposal tools, which still end in review. The built-in `/app` and `/skill` add their own instructions and tools. Removing a skill hides it and keeps its versions.

An app proposal is one self-contained HTML document of at most 256 KiB, with a short name, a one-sentence description and up to 16 declared collections, each read or write. Static review notes flag web resources, network APIs, browser storage, `innerHTML` and undeclared data use. They inform review; isolation never depends on them. app.read returns an existing app's current source in pieces of 24 KiB, at most 96 KiB per job, before a revision. Approval binds the proposal digest, publishes `extensions/miniapps/<id>/<version>/index.html` and `app.json` create-only, turns that version on, and records a device-local grant for exactly its declared collections. Grants live with device control state, never in Home backups, so a restored app stays off until the person turns it on. Choosing another version grants that version's declared access. Turning an app off or removing it deletes the grant and keeps its versions and data. The host serves a version only while its bytes match the recorded hash.

Apps store records through `window.sevra`: info, list, get, create, update, archive and restore. The broker takes the app's identity from the host's own record of the app and its active version, never from the request. It allows only collections that are both granted on this device and declared by the active version. Each record is a db.md document of type `sevra-app-record` at `records/app-data/<collection>/<id>.md`, written through the ordinary Home transaction with a revision number; update, archive and restore must name the current revision. Record data is a JSON object of at most 64 KiB, nesting depth 16, 512 fields per object and 4,096 items per array. A collection holds at most 5,000 records and a request is at most 256 KiB. Data belongs to the Home, not the app: an app's versions share it and removal keeps it. Sevra assigns record ids, and the model's app guidance says so: to keep one value, use the first listed record and create one only when the list is empty. Changes reach an open app as `sevra-change` events only when that app did not make them. A real model-built app looked for a record id it chose itself and reloaded on every change. With an app's own saves echoed back, a check that reproduces that pattern counted 40 records within about four seconds. Each app may send a burst of 120 write requests, valid or not, and then 2 per second; further writes are refused as busy. The review preview applies the same rules to its scratch data. Requests are refused while saving is paused, during shutdown and before a restored Home is reviewed. A Home document changed outside Sevra pauses saving.

Each app runs in its own `WKWebView` with a non-persistent data store. A custom `sevra-app://app/` scheme serves only the approved bytes, with a content security policy that allows inline script and style and data or blob media and denies everything else, including connections, frames, workers, plugins, form submission and base changes. A compiled content rule list blocks every load outside that scheme. The view's HTTP CONNECT and SOCKS proxies point to a loopback port that Sevra binds without listening, so anything that connects outside a load is refused. WebKit's peer connection, link preconnect, DNS prefetch, preload and speculative prefetch features are switched off through WebKit's feature flags, and peer connection APIs are removed in every frame. Peer connections, link preconnects and DNS prefetches bypass content rules and the proxy, so unless WebKit reads back all three as off, the app does not run. Navigation other than reloading the app's own document is cancelled. Popups and downloads are refused, web links go to the existing confirmation sheet, camera and microphone requests are denied, full screen and AirPlay are off, and at most five alert or confirm dialogs are shown. Only the main frame of the app's own origin can call the bridge. A review preview runs the draft in the same host against scratch data that never reaches Home and ends with the view. If the web content process ends, the app reports it and its saved data is unchanged.

Known residuals. The feature switches use WebKit's private preference interfaces and must be rechecked on each macOS release. A WebKit that drops them stops apps from running until Sevra is updated. An app has no CPU or memory ceiling beyond WebKit's own process limits, so a busy app runs until the person closes it.

## Context and job budgets
Since September 17 the app plans the model with a 32,768-token context window, the engine's smallest automatic window, instead of 8,192 tokens. Documents, file changes and apps need the room. At a 10 GB target with drafts and vision off, `slotstream doctor` 0.2.20 plans the same 9.0 GB peak for both windows and 20 instead of 21 cached experts per layer. It estimates that a prompt filling the window waits about 6.4 minutes before its first token at that target; one job's source text is bounded near half the window.

A plain answer may use up to 4,096 reply tokens. A job that can stage changes or propose a document, app or skill may use up to 12,288. Both are reduced to the room left in the window, and a request with less than 256 tokens of room is refused. A thinking plain answer keeps its 1,024-token reply cap; a thinking turn that can stage work keeps the job's budget instead. A job has at most 12 model rounds and 45 minutes. A model response has at most 8 calls, and each tool string is at most 1 MiB. These are development operating bounds for a local decode rate of a few to sixteen tokens per second, not measured optima. Revise them with measured workflows and paired timings.

## Adaptive memory limits
The custom memory preference maps to Slotstream’s adaptive total-process ceiling, not a fixed cache or a RAM percentage. Its selected ceiling survives pressure-driven shrink/grow, context planning and vision reservations. Real availability and supported GPU/system headroom still bound allocation. Diagnostics and budgeted startup share a feasibility check; the engine reads availability again before loading. Idle readiness and deferred changes retain their existing lifecycle.
