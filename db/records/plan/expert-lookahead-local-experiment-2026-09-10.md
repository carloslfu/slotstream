### 1. Objective, scope and fixed decisions

Build **Expert Lookahead**, a learned expert-ranking and prefetch system for the existing Slotstream checkpoint. It must improve measured native decode throughput while preserving the chosen baseline's actual routing, expert weight bytes, numerical execution and output behavior.

The first experiment runs entirely on the existing M5 Pro with 48 GB unified memory and internal SSD. Rental budget is zero. Start with a 10,000-output-token pilot, then expand to approximately 50,000 outputs only after the pilot establishes valid features and a plausible performance opportunity. Train a roughly 5M-parameter whole-pass predictor and compare it with cheap routing baselines and a short-lookahead predictor. The initial win criterion is at least 10% repeatable throughput improvement at equal total memory, with exact correctness gates passing.

The teacher remains frozen: Qwen3.8-Flash-Next, approximately 125B parameters plus 51B ngram tables, in the existing roughly 104 GB quantized checkpoint. Only the prediction network is trained. Expert caches contain weights, not reusable token outputs. Predicting or substituting expert activations, changing selected experts, skipping the authoritative router, and changing MTP depth are outside the first experiment.

The primary execution mode is text, MTP enabled at the adopted depth two (pending token plus two draft positions), fixed prefill chunk 256, prefix retention disabled, elastic resizing disabled, and the current resolved deployment optimizations. Greedy generation is the primary performance workload; seeded sampling is also a correctness gate. Qualification applies to this exact mode. Other modes retain the current path until separately qualified. An explicitly requested missing, malformed or incompatible prediction pack fails validation before allocation; this is distinct from a valid pack being bypassed for an unsupported execution mode. In particular, do not load the MTP head merely to obtain predictor features when MTP is off.

P0 must explicitly freeze `SLOTSTREAM_DRAFT_DEPTH=2` for collection and every B0/B1/B2 arm, with adaptive speculation and experimental draft-tail shortening disabled. Do not rely on an executable's default: the installed public 0.2.14 artifact still defaults to one. Bind the actual candidate/source identity, three-position feature schema and pack compatibility before data collection; preserve normal context-bound shortening.

The completed OPT00–OPT36 program stays complete. This is a new experiment, not a reopening of its rejected accelerators. When this plan is later executed, continue through its local work packages and qualifying 10k-to-50k expansion without asking for a new approval at every step; the current task authorizes preparation of the plan, not starting those runs. The old M1 proxy/cloud proposal is historical; this plan uses the actual native teacher locally. No installed executable replacement, default activation, publication or release is part of the initial proof.

### 4. Candidate architecture and causal feature contract

#### Whole-pass model G128

For main verification position zero, use the previous committed main context `state.lastMulti` (10,240 values) and the known pending token's base embedding (2,560 values). For position one, use the already-computed MTP multi after consuming the pending token together with the first draft token's embedding. For position two, use the MTP multi after consuming the first draft together with the second draft token's embedding. The latter two contexts are draft proxies, not uncomputed main-model hidden states. Retain these existing head outputs without an additional head step, and add a three-entry hidden bias for position/feature kind. Charge retained features, any missing embedding read, feature copies and all three predictor rows. Near a context bound, emit features only for positions the native pass actually evaluates.

Every position's inputs must be available before `allLogitsWithMultiChecked(verifyIds, state:)`. Never train either draft position using a main-model state from that same future verification pass. Never drop a rejected draft position from the labels: its main-model experts were still evaluated and loaded. If features are absent or the mode is unsupported, use ordinary demand loading.

Normalize each input block with fixed RMS normalization, epsilon `1e-6`. Trainable computation is `12,800 -> width -> 24,576`, with SiLU and biases. Interpret the output as 48 independent 512-expert ranking vectors. For the three positions, form a demand ranking over the union of `(layer, expert)` keys; calibrate this union on validation rather than assuming independent position probabilities. Each distinct record has one shared read ticket even when multiple positions predict or demand it; retain the per-position labels separately.

| Width | Base MLP parameters, including biases | FP16 base weights | Role |
| --- | ---: | ---: | --- |
| 64 | 2,416,704 | 4.83 MB | Capacity/overhead lower bound |
| 128 | 4,808,832 | 9.62 MB | Initial candidate |
| 256 | 9,593,088 | 19.19 MB | Capacity check only if justified |

The three position biases add `3*width` parameters (384 for G128). Fixed normalization adds none. These counts exclude implementation workspaces and the optional refiner. G128 is therefore approximately 4.81M parameters, not a 5M language model. Use native MLX as the first runtime implementation. At the pilot, benchmark CPU-device versus GPU-device prediction with the same exported pack, including feature materialization and score transfer; select by net exposed overhead while preserving the target stream. No background task may invoke MLX unless separately qualified for its ownership/stream semantics. Start with FP32 weights for Python/Swift comparison, then test FP16 export; lower-precision prediction may change rankings but must never change target arithmetic. Retain the faster validated representation.

#### Short-lookahead and refinement

Train a shared conditional model `L128`: normalized `x2` from completed layer L, learned source-layer and horizon embeddings of width 16 each, hidden width 128, and 512 output scores for target layer `L+d`, where `d` is one of 1, 2, 4, 8. At this geometry it is 398,784 parameters at the stated geometry. Mask nonexistent target layers. Apply L128 to each actually evaluated position of the completed layer, with its own `x2` row and matching future-layer target row; union the predicted record keys before admission. Batch these rows where useful and charge all feature, model and transfer work. Layer/expert identities are not interchangeable: condition on layer and retain target-specific reporting.

Use full-layer pilot captures to compare horizons and layers. Initially deploy either G128 or a short-lookahead schedule selected on validation. Test combined G128 + L128 only if both add timely coverage: initial refinement anchors are after zero-based layers `3, 7, 11, ..., 43`, forecasting future valid horizons. Do not execute a refinement for every future layer just because it can be evaluated offline. Measure batching, feature extraction, model execution and score transfer together.

The initial size range is thus about 2.4M to 9.6M for the global model, optionally plus the small refiner. There is no evidence that 48 separately trained large predictors are optimal. A per-layer model can be a later capacity diagnostic if shared conditioning underfits; it is not the first architecture grid.

#### Required baselines and ablations

Compare ordinary CLOCK/demand loading; per-layer training-set frequency; previous observed pass routes with causal updates; G64/G128; L128 at fixed horizons; and an offline perfect-future oracle under the same bounded scheduler. Test G256 only if G128 underfits or its validation curve supports capacity. Test G128+L128 only if coverage is complementary. Frequency and recent routes must use the same byte budget and deadline rules. Filter resident experts for every predictor. Every policy in this comparison, including a non-learned baseline, is an eligible final candidate: the experiment tests bounded prefetch, and the learned-versus-cheap coverage margin decides only whether training continues.

At the pilot stage, run one seed per candidate. Repeat the leading learned candidate with three fixed seeds before selecting the final pack. A model with better offline accuracy but slower measured prediction can lose selection. The oracle is a diagnostic upper bound with forbidden hindsight, never a deployable performance result.

Record the interpreter and exact packages. A trainer environment may use the available newer version, but export is qualified against the native Swift/MLX build. Use balanced multilabel BCE over each layer's selected ten versus the other 502 experts, so predicting all negatives cannot win. Add miss-focused sample weighting only as a named ablation after the general predictor works.

The trainer consumes bounded batches from shards; it does not load the teacher or all features into GPU memory. Start with an 8 GB process working-set ceiling, at least 12 GB reclaimable before launch, and no teacher, benchmark or large build running concurrently. The small network normally needs much less, but the ceiling includes loader, optimizer, runtime cache and activations. A measured breach stops the run and leads to a smaller batch or buffer before retrying under a new recorded attempt.

#### Metrics and scheduler simulation

Implement proposed `Tools/expert_lookahead.py` commands for `validate-data`, `train`, `evaluate`, `export` and `report`, with strict JSON protocols. Use the existing `Tools/cache_policy_probe.py` as the batch-pinning reference, not the older hindsight-hot-set simulator. The no-prefetch replay must reproduce native miss counts and requested bytes at recorded request boundaries before its predictive results are trusted. Record initial slot mapping, CLOCK hand and reference bits, and all prefill admissions needed for this match. Cold-request training traces alone do not establish warmed-cache utility.

Report ordinary recall@10/16/24/32 by layer/horizon/feature kind, but select using:

1. **Timely missing-byte coverage:** baseline-demand-miss bytes available in staged buffers by their demand deadline, divided by baseline-demand-miss bytes. Each record is counted under an explicit deduplication/reload rule.
2. **Useful-prefetch precision:** consumed prefetched bytes divided by all prefetched bytes, including cancelled/expired reads. Report partially completed wasted bytes separately.
3. **Traffic amplification:** all candidate requested file bytes divided by baseline requested file bytes, including demand reads, speculative reads, failures and reloads.
4. Exposed demand waits, predictor/feature-transfer overhead, staging high-water, extra cache misses caused by reduced capacity or retention changes, and per-layer arrival slack.
5. Native emitted-token throughput, time per output token, total request duration, TTFT, tail latency, resource exclusions and exact correctness. These decide adoption.

Baseline timestamps alone overestimate future lead time when earlier stalls are removed. Run a causal event simulation that advances deadlines as the candidate becomes faster, and vary service times under shared CPU/SSD/RAM contention. Calibrate using unprofiled native observations and the isolated attribution evidence; do not turn simulated milliseconds into measured gains. The perfect oracle is subject to the same staging capacity, release lifetime, queue lanes and cache budget as learned candidates.

Freeze candidate ranking rules and thresholds before unsealing test data. Proposed useful targets are 50–70% timely missing-byte coverage, no more than 1.20x total file bytes, predictor plus scheduler exposed overhead under 2% of baseline decode, and at least 10% actual throughput gain. These are engineering targets, not four mathematically equivalent quantities. Use native demand-wait events to distinguish a ready raw buffer from a fully installed cache slot; v0 does not promise that GPU scatter time is hidden. A target miss triggers diagnosis; only correctness/resource gates are immediate hard stops. The final throughput criterion cannot be replaced by hitting the classifier targets.

### 7. Bounded prefetch runtime, version zero

The first runtime performs **raw staging prefetch only**. It does not speculatively insert experts into the slot pool, change CLOCK retention, or reserve future pool victims. The normal router and demand path decide which bytes enter which slots. This avoids turning an incorrect forecast into a speculative cache eviction while still testing whether reads can overlap useful work.

Implement proposed `ExpertPrefetch.swift` with an immutable ticket identity `(request, pass, model/store revision, feature/predictor version, key set)`. A ticket moves through queued, reading, ready, adopted or discarded/error. Every ownership transfer is single-use. Workers have immutable checked file descriptors/offsets and their own raw buffers; only the model owner touches MLX, pool maps, pins and model state.

The scheduler starts forecasts before main verification. At each existing completed-layer boundary it updates eligibility, drops expired candidates, and starts a bounded set of near-deadline reads. Filter resident/loading/ready keys at admission; retain soft forecasts for resident keys so a later eviction can make them eligible again; avoid duplicate reads; rerank soft queued work after a refinement. Distant layer scores stay metadata until their deadline window approaches. Start candidate ranking caps at top 16 and 24 per position/layer, and choose admission thresholds on validation under the global byte cap. These are candidates to rank, not instructions to load that many experts immediately.

Raw payload capacity is at most **32 expert records**, or **88,473,600 bytes**, across reading, ready and adopted-but-not-yet-released speculative buffers. This is one shared cap across all positions, layers and predictors, not one cap per draft; additional positions do not multiply the I/O lanes or memory reservation. Initially reserve **128 MiB incremental runtime memory** for predictor weights/workspace, metadata and these buffers, inside the existing total process target. Ordinary demand staging already belongs to the baseline ledger; both must fit simultaneously. Count each physical allocation once and keep it charged until the consuming GPU graph releases it. If the measured predictor representation/workspace exceeds the reserve, shrink staging or revise the declared reserve before testing; never conceal the excess in a larger process target.

Deduct the incremental reservation before solving expert capacity. A 128 MiB reservation corresponds to at least 49 current expert records if paid entirely from the pool. That is arithmetic, not a claimed final planner slot count. Benchmark actual plans. Do not assume model weights are the only incremental memory or retain aliases that cause a full expert arena copy.

Share a bounded I/O lane budget with demand reads. Start at the existing default checked-read queue depth, not an additional full set of lanes per speculative ticket. Demand has highest priority; stop launching speculative work when demand needs bandwidth. A prediction must not set CLOCK reference bits or pins; only real demand does so in v0. Cancellation is checked between checked read operations, including EINTR handling; an already blocked `pread` cannot be preempted instantly. Never claim zero cancellation latency. Avoid head-of-line waits on an unrelated multi-layer batch: completion/adoption must be available per record or per same-deadline mini-batch, while retaining the nine-piece record's all-or-nothing validity. A single owner-side scheduler enforces lane and byte limits across speculative and ordinary demand reads; replacing `concurrentPerform` with a shared executor must preserve checked-read joining and error propagation.

When `ensureCore` sees actual misses, preserve its current key order, hit pins and victim reservation. For a complete matching raw ticket, adopt the bytes into the usual MLX staging/scatter dependencies. For a matching in-flight record, promote it to demand and join it without launching a duplicate. For absent, stale or unusable data, use the ordinary checked read. Adoption is zero-copy by default: a ready ticket's nine buffers become their own MLX staging arrays and scatter per record or per same-deadline mini-batch, while the demand batch keeps its existing contiguous layout, so mixed ready/demand records are assembled by ordering scatters in the logical demand order, not by copying bytes. A host copy into the contiguous batch layout is allowed only as a measured fallback: copying every adopted record would repeat a 2,764,800-byte copy per miss, so its bytes and time are reported in C09/B2 and count against the 2% overhead budget. Publish slot mappings only after all nine pieces are complete and the required scatter dependency is installed. A partial read must not become a cache hit. Completed-reader cancellation and adopted-buffer lifetime tests must prove that freeing a ticket cannot free bytes still referenced by a scatter graph.

A failure on a purely speculative unused read records the failure and disables/discards the hint as appropriate; it must not expose invalid bytes or fail an otherwise valid unrelated demand. A requested record still goes through the authoritative checked-read error policy. Model-file mutation, identity mismatch or checkpoint corruption is not silently treated as a harmless predictor miss.

On request completion, error or cancellation, stop submissions, join owned readers and release buffers. Clear future-pass predictions after MTP reconciliation. On model/store replacement, pool resize, prefix restoration or request reuse, invalidate old ticket identities before new work; join before closing descriptors or releasing ownership. The next request must not consume a prior request's speculative ticket. Close and drain the scheduler before a between-request governor resize. Byte-compatible cache entries already installed by real demand remain governed by normal cache rules.

### 9. Native benchmark and decision protocol

Use one frozen candidate binary with experimental control off/on where possible, and verify its off path against the pristine baseline. Use no hidden-feature trace, tensor snapshot or intrusive GPU profiler in headline timing. Keep lightweight counter overhead common and check a counters-off control on the pilot. Compute a rolling main-router digest and count from IDs already materialized on the host in both arms; full route/logit tensor comparisons belong to separate correctness runs. Bind corpus, pack, driver and binary hashes before collecting final results.

Three comparisons distinguish the mechanisms:

- **B0, headline:** current deployment with its full ordinary cache at the fixed total budget, versus predictor plus charged memory at that same total budget. This is the user-relevant gain.
- **B1, mechanism:** identical reduced slot count/reservation in both arms, predictor/prefetch off versus on. This separates overlap benefit from lost cache capacity; do not advertise it as B0.
- **B2, overhead:** same candidate pack/features executing in shadow mode, without reads, against its matching no-predictor capacity control. This reveals feature, model and host overhead.

Run B1/B2 on pilot validation fixtures, select a candidate, then freeze it. Do not run a full matrix of every width, horizon and cache size. The final held-out B0 cohort has six workload families, two frozen prompts per family, and three preplanned paired rounds per prompt: 36 pairs, 72 measured arms. Its twelve prompts are drawn from the sealed test families only; no B0 prompt, paraphrase, template or source document may belong to a train or validation family, and the frozen corpus manifest records that check. Each arm starts a fresh server, performs the same-prompt 128-output warmup, then measures up to 512 outputs. Greedy sampling, seed 42, thinking disabled, maximum context 32,768, prefill chunk 256 and all other controls remain fixed. Arm order alternates by prompt/round and family order rotates. Keep EOS and all work counters; an earlier clean EOS is valid if both arms match exactly, but report its shorter length and do not call it a 512-output observation.

**Any target-route, logit or output mismatch is a correctness failure of the candidate, including a mismatch in a resource-contaminated run; preserve it and investigate before proceeding. It cannot be hidden by excluding a timing pair. An actual candidate budget overrun, unsafe lifetime or unexplained runtime failure likewise blocks qualification until resolved.** A pair is timing-eligible only if both arms complete, match exact token outputs and required settings, stay within their budgets, and have no observed swap changes, non-nominal thermal state or declared contention during the measured request. Preserve excluded rows. Require at least two clean pairs per prompt out of its three frozen rounds. There are no replacement pairs inside this cohort. If eligibility is insufficient, report inconclusive and design a new named cohort after the environmental issue is resolved.

For each prompt compute the median paired throughput ratio `TPS_on/TPS_off`; aggregate with equal family weight using geometric means. Report all prompt/family ratios, absolute TPS, time per output, request duration, TTFT, p95 native per-token callback interval (separately from HTTP chunk arrival), read traffic, hit rate, MTP accepted/evaluated counts, memory and exclusion rate. Avoid pooled-token weighting that lets a long easy task dominate. Use 10,000 bootstrap draws with seed 1729, resampling prompts within each family and eligible paired rounds within each selected prompt; keep family weights equal. Report the 95% interval and explicitly limit inference to this small frozen workload set.

**Initial proof passes only when:** all relevant C01–C10 checks pass; B0 aggregate throughput ratio is at least 1.10; the lower bootstrap bound is above 1.00; no family median throughput ratio is below 0.95; and no family median total-request duration regresses by more than 5%. Investigate material TTFT/tail regressions before calling the candidate usable. A positive point estimate with insufficient clean evidence is inconclusive, not success. Lower than 10% can be recorded as a small measured benefit but does not close this experiment's success gate.

The 50k training-data budget excludes benchmark outputs. This full B0 design can add up to 36,864 measured outputs and 9,216 warmup outputs. Existing release-wide checks are additional work and are not included in the first model-training estimate.

### 11. Scaling rules and conditional extensions

Stop adding data when the fixed validation learning curve shows less than approximately 2–3 percentage points of extra timely missing-byte coverage and less than 1–2% projected incremental throughput from the latest near-doubling, within its uncertainty. These are stopping heuristics, not measured universal sample-complexity laws. Use actual native screens to check the projection. Do not claim 50k is the mathematical optimum.

If both training and validation utility are low, compare G256 and shorter horizons or better causal features before collecting more. If training is strong but held-out utility is weak, prioritize new source families and undercovered contexts. If predictions are accurate but late, change deadlines, batching or feature availability. If on-time coverage rises but TPS does not, investigate read contention, staging copies, CPU work and cache capacity. Repeated epochs cannot fix missing information or an already saturated critical path.

The initial collection budget in this plan is scoped by its frozen local run protocol to roughly 50k outputs, not an automatic unbounded search. A larger 100k/200k successor needs a new recorded decision and resource/time estimate based on the measured curve. Preserve the original held-out test result; after using it for a design decision, obtain a fresh untouched test cohort for the successor. No cloud expenditure is implied by any scaling result.

| --- | --- | --- |
| Forecast-guided retention/admission | Raw prefetch is useful but traffic or lost residency still limits speed. | Separate policy ablation versus CLOCK at equal total memory, causal next-use estimates, bounded victim search, no permanent speculative pins. Predict retention horizons such as 8/32 future outputs only with exact emitted/physical-position labels. |
| Final-prefill cache seeding | Cold decode misses dominate and a forecast exists before each relevant layer's final sweep admission ends. | Hook `admitOnSweep`/commit timing correctly; charge preload reads and TTFT. Predicting all layers does not make their dependent hidden-state computation parallel. Predicting expert outputs would change answers unless verified by the original computation, which removes the obvious saving. Keep those distinctions explicit. Research such as [ProMoE](https://arxiv.org/html/2410.22134v3), [pre-attention prediction](https://arxiv.org/abs/2511.10676), and [SP-MoE](https://arxiv.org/abs/2510.10302) motivates feature lookahead and scheduling; their architecture, memory placement and reported gains are not this experiment's baseline.
